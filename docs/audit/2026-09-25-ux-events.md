# UX Audit — Create & Join Events (UX-CEVT-01..11, UX-JEVT-01..14)

Transcribed from `UX-Audit-Create-Join-Events.docx.pdf`, section "11. Events". 25 items.

Status: **transcribed and planned.** See `2026-09-25-ux-events-plan.md` for the pull requests and the
decisions taken with the product owner on 2026-09-25, which are not to be re-litigated.

## Event rules (fixed, not configurable by the organizer)

| Rule | Behaviour |
| --- | --- |
| Confirmation deadline | Players can confirm attendance up to 6 hours before the event starts. |
| Withdrawal deadline | Players can leave up to 12 hours before it starts. After that, leaving shows that the in-app deadline has passed, with the organizer contact. |
| Organizer override | The organizer can add or remove any player at any time, with no deadline. |
| Waiting list | Unlimited. When a confirmed player withdraws, everyone on the waiting list is notified at the same time and the spot goes to whoever confirms first. Nobody is confirmed automatically. |
| Team events | Spots are counted per player. A confirmed pair fills two spots. A player looking for a partner is marked as interested and fills none. Pairs take spots in the order they confirm. |

## 11.1 Create Event

### UX-CEVT-01

**Location:** Create Event — Wizard shell

**Problem:** The wizard chrome is inconsistent across steps. The close action is the word "Fechar" instead of an icon. Progress is shown twice — as "Passo N de 10" on the left and a row of dots on the right. Navigation buttons sit at the bottom of the screen as "Voltar" and "Seguinte", including on steps where a single tap already determines the answer, so the user has to select and then confirm the same thing. Step titles do not name what is being set.

**Suggestion:** Apply the same chrome to every step. Header:
- Back button as a left arrow icon on the left, matching the pattern used in onboarding. It is absent on the first step, where there is nothing to go back to — only the close action is shown.
- Close ( ✕ ) icon in the top-right corner, replacing the "Fechar" label. It opens a confirmation sheet warning the information will be lost.
- Progress bar spanning the width below the header, with the percentage on its right on the same line. Remove the "Passo N de N" label and the dots.
- The bar reflects the real number of steps for that path — a manually added venue skips the Courts step, and a public group event skips Invite players. Advancing:
- Steps that are a single choice from a list advance immediately on tap. No "Seguinte" button, and no selected state left on the card — the tap is the answer.
- Steps that require setting more than one value keep a primary button fixed at the bottom.
- The "Voltar" button is removed from every step — going back is the header arrow. Titles:
- Each step title names what is being set: Group, Format, Players, Scoring, Location, Courts, Date, Preferences, Details, Invite players. Multi-step creation flows carry both controls per UX-GLOB-01. Bottom sheet per UX-GLOB-02. Submission feedback per UX-GLOB-06.

### UX-CEVT-02

**Location:** Create Event — Group

**Problem:** The step is titled "Onde?", which describes location rather than group. The group cards show only the name, with no image and no member count. "Continuar sem grupo" is a card in the list, competing visually with the actual groups, and the explanation of what an event without a group means sits as small print below the list.

**Suggestion:**
- Title the step "Group".
- Each group card shows the group thumbnail, name and number of participants.
- Tapping a group selects it and advances immediately.
- Move "Continue without group" out of the list into a fixed button at the bottom of the screen. The button label is just that — the explanation that an event without a group counts toward no ranking sits as small supporting text below the button, not inside it.
- Remove the small print below the list.
- Tapping it opens a confirmation sheet titled "Event without group", explaining the event will not count toward any ranking and will have only its own leaderboard, with primary and secondary actions.
- An event without a group is a normal path, not an edge case. It is how an organizer runs a one-off event with people who are not in their communities, or not on the app at all, and it stays available to users who do belong to groups. Bottom sheet per UX-GLOB-02. Card orientation per UX-GLOB-09.

### UX-CEVT-03

**Location:** Create Event — Format Problem: The step is titled "Formato" but requires a separate "Seguinte" tap after the selection is made.

**Suggestion:**
- Three cards: Americano, Mexicano, Up & Down, each with its description.
- Tapping one selects it and advances immediately.
- No "Seguinte" button on this step.

### UX-CEVT-04

**Location:** Create Event — Players

**Problem:** The step does not indicate which format was chosen in the previous step, so the user loses the context of what they are specifying. It also requires a separate confirmation tap.

**Suggestion:**
- Display the format selected in the previous step as a read-only chip above the options.
- Three cards: Classic, Mixed, Team, each with its description.
- Tapping one selects it and advances immediately.
- No "Seguinte" button on this step.
- The three are mutually exclusive modalities, and neither they nor the format can be changed after the event is created (UX-LIVE-20).

### UX-CEVT-05

**Location:** Create Event — Scoring

**Problem:** The three scoring types are listed as flat options, and the value that each one requires is set in a separate field below the list rather than inside the option itself.

**Suggestion:** Three collapsed cards — Points, Time, Classic sets. Selecting one expands it in place and collapses the others. Points:
- Expands to a row of preset values — 8, 11, 16, 21, 24, 32, 40 and Custom — with 32 selected by default.
- Custom opens a bottom sheet with a centred numeric input, the numeric keyboard, and a save button visible above it. Time:
- Expands to a slider, default 10 minutes, minimum 1, maximum 90. Classic sets:
- Selection only, no additional value. • This step keeps a primary button fixed at the bottom, since a value must be set before advancing. Bottom sheet per UX-GLOB-02.

### UX-CEVT-06

**Location:** Create Event —
Location:

**Problem:** The location step has no working logic. It shows a search field, a manual entry link, separate fields for venue name and address, and a "Localizar pela morada" action, all on the same screen, with no distinction between picking an existing venue and creating one. There is no venue library, no results list, and no path for an event without a location.

**Suggestion:** Rebuild the step around three distinct scenarios. The initial screen has a search input, an "Add manually" action below it, and the list of existing venues. Scenario 1 — pick an existing venue:
- The list shows venues already registered in the app, curated by the platform admins.
- Each venue is a card with image, name, address and number of courts.
- Selecting one advances to the Courts step (UX-CEVT-07). Scenario 2 — add a venue manually:
- Reached from "Add manually", or from the "Location not found" state when the search returns nothing.
- Fields: venue name (optional), address, number of courts, and optionally a name for each court.
- A banner explains that this venue serves this event only, and that having it added officially to the app requires contacting the app.
- The venue is temporary data for this event. It is not added to the registry and does not appear for anyone else.
- Advancing goes straight past the Courts step — the courts were already defined here. Scenario 3 — no location:
- A secondary "Do not want to add a location" action fixed at the bottom.
- Advances to a Courts step containing only the court count selector.
- This is a search over a curated venue registry, not a map search. It has no geolocation step and is a different mechanism from the location picker used when creating a community. Empty state per UX-GLOB-03. Search input per UX-GLOB-05. Card orientation per UX-GLOB-09.

### UX-CEVT-07

**Location:** Create Event — Courts

**Problem:** The step shows only a court count selector with no relation to the venue chosen, and there is no way to pick which courts of a venue will be used.

**Suggestion:** The step adapts to how the location was set. Venue selected from the registry:
- Two options at the top: "Select courts" and "Have not reserved yet".
- Select courts lists the available courts with checkboxes, plus a banner stating that selecting courts here does not reserve them — bookings are made directly with the club, and this is only an indication for the players.
- Have not reserved yet shows only the court count selector. Venue added manually or no location:
- Only the court count selector, since there is no court list to choose from.
- In every case, the court count determines the capacity, displayed below the selector: 4 players per court.
- On a mixed event the capacity is split evenly, half the spots per gender, since every pair is one man and one woman (UX-MEVT-25).

### UX-CEVT-08

**Location:** Create Event — Date

**Problem:** The date row scrolls horizontally but shows no month, so a date in another month cannot be identified. The start time uses plus and minus steppers for hour and minutes instead of letting the user pick a time. Duration uses a stepper with no presets. The recurrence card is missing entirely, and there is no summary of when the event will happen. Everything is packed too tightly together.

**Suggestion:** Four cards, with clear spacing between them. Date:
- Horizontal scroller of days. When the scroll crosses into another month, the month abbreviation appears inline in the row. Time:
- Three period tabs — Morning, Afternoon, Evening — each revealing preset start times in a grid. The user picks a time; no steppers. Duration:
- Three presets — 60, 90, 120 minutes — with 60 selected by default, plus a Custom option opening a bottom sheet with a numeric input, same pattern as the custom points in UX-CEVT-05. Repeat every week:
- A card with a toggle, described as setting the event as recurrent.
- When enabled, it expands to show when the invite is sent for the next occurrence — 1 week before, 5 days before, 3 days before. Summary:
- A box stating when the event will happen, and the next occurrence when recurrence is on.
- The box is fixed to the bottom together with the primary button, not scrolling with the content above it. Bottom sheet per UX-GLOB-02.

### UX-CEVT-09

**Location:** Create Event — Preferences

**Problem:** The toggles sit loose on the screen instead of inside cards, and the values each toggle enables — extra spots, fee amount, payment method — appear as separate fields below rather than inside the option they belong to. When the event is private there is no warning about the consequence for the ranking.

**Suggestion:** Group everything into cards, and every value a toggle enables appears inside that same card. Game Details:
- "Allow stand by players" toggle, described as letting extra players join the rotation and sending them to the waitlist when disabled. When on, expands to an extra spots counter. Invite Details:
- "Private event" toggle, described as only invited players being able to see the event.
- When the event has no group, this toggle is on and disabled — independent events are always private. The line below states this.
- When the event has a group and the toggle is on, show a banner stating that private events do not count toward the group ranking. In that case only the players invited in the last step take part, not the whole group.
- "Entrance fee" toggle; when on, expands to payment method tabs — Cash, At Club, MB WAY — plus the amount field and, for MB WAY, the number field. Permissions:
- "Players can submit their own results" toggle. This is what enables players to enter the score of their own match while the event runs (UX-LIVE-08). I am...
- Two options: Organizing only, Organizing and playing.
- This only determines whether the organizer starts already confirmed. It never prevents them from joining later (UX-MEVT-02).

### UX-CEVT-10

**Location:** Create Event — Details

**Problem:** The image field is a large empty box labelled "Adicionar imagem", which differs from the image component used when creating a group and a community.

**Suggestion:**
- Name and description fields.
- Thumbnail using the same component as Create Group and Create Community: a row of preset images plus a custom upload option, with change and remove actions appearing in the image top-right corner once set.
- Same behaviour across the three flows.

### UX-CEVT-11

**Location:** Create Event — Invite players

**Problem:** The step is a form with three separate fields — name, email and phone — which is not how players are invited anywhere else in the app. There is no search, no way to pick from existing players, and the step appears even for public group events, where every member of the group is invited automatically.

**Suggestion:** When the step appears:
- Whenever the event is private — which includes every event without a group, since those are always private.
- For public group events, every member of the group is invited automatically and this step is skipped. Structure:
- Search input at the top, listing platform players with photo, name and a selection control — the same pattern as the members screens.
- "+ Add manually" in the top-right corner.
- A primary button at the bottom, and a secondary "I will invite later" below it, which creates the event with no players yet. Add manually:
- Opens a bottom sheet with a name field and, for mixed events, a gender selector.
- A note stating the player will be created and confirmed for this event only, carries no history, and appears in no ranking. • It should only be used for someone who has no access to the app and will not have it before the event.
- Saving adds them straight to the confirmed list. This is the most common path on events without a group, which often gather people who are not on the app.
- When the search returns nothing, show the standard empty state — icon, title, description — with "Add manually" as its CTA. Bottom sheet per UX-GLOB-02. Empty state per UX-GLOB-03. Avatars per UX-GLOB-04. Search input per UX-GLOB-05.

## 11.2 Join Event

### UX-JEVT-01

**Location:** Events — Event List

**Problem:** Events without an image show a plain grey block instead of a placeholder. Every event carries an "Em breve" tag, which says nothing since all listed events are upcoming. Two states are missing: events the user was invited to but has not answered, and events that have already happened.

**Suggestion:**
- Four tabs: All, Organizing, Going, Pending.
- Pending lists events the user was invited to and has not answered yet.
- Above the tabs, a "Show past events" toggle, off by default. When enabled, past events appear in the list alongside the upcoming ones, in every tab.
- The toggle exists because events without a group would otherwise have nowhere to be seen. Events that belonged to a group also remain accessible in that group Events screen (UX-GRP-05).
- Remove the "Em breve" tag from the cards.
- When an event has no image, show a thumbnail with an icon placeholder, never an empty grey block.
- No search icon in the header. Global search lives on Explore (UX-GLOB-05). Header per UX-GLOB-01. Empty state per UX-GLOB-03. Card orientation per UX-GLOB-09.

### UX-JEVT-02

**Location:** Events — Event Detail

**Problem:** The information is ordered and presented differently from the reference design: it is a flat list of label-and-value rows with no hierarchy. There is no " ⋯ " action in the header. The player card shows only a number, with no way to open the full list and no sense of how many spots are left. The format, group, courts, scoring and fee are text rows rather than distinct components, and the location is not tappable.

**Suggestion:** This is the base structure of the event screen. Every other event state reuses it and changes only the bottom area and the top banner. Header:
- Back button on the left, " ⋯ " in the top-right corner (UX-JEVT-06).
- Event image below the header, or a placeholder when there is none. Identity:
- Event name as the title, with date, time and location as the subtitle. Players:
- A card showing three thumbnails of confirmed players, "Players" as the title, and the confirmed count against the total capacity as the subtitle, so the remaining spots are visible without opening anything.
- A chevron opens the full player list (UX-JEVT-08). Badges:
- Event type and group, side by side as badges. Description:
- The event description below the badges. Widgets:
- Three widgets side by side: Courts, Scoring, Fee — each showing how many courts, how the scoring works, and the entry fee. Read-only, including for the organizer. Organizer:
- A card with the organizer photo, name and a chevron opening their profile. Location:
- A card with the venue name and address, opening the native maps app. Bottom area:
- Fixed to the bottom, and its content depends on the state — see UX-JEVT-03 to UX-JEVT-05. For the organizer, see UX-MEVT-01, which keeps this whole body and changes only the header and the bottom area. Header per UX-GLOB-01. Avatars per UX-GLOB-04.

### UX-JEVT-03

**Location:** Events — Invited

**Problem:** The invitation appears as a row of text with Accept and Decline buttons at the bottom, with no indication of who invited the user. On accepting, only the bottom area changes — there is no confirmation screen and no way to add the event to a calendar. Suggestion: Invited state:
- The bottom area shows the inviter photo, name and the line stating they invited you, with "Decline" as secondary and "Accept" as primary below it.
- Invitations are only sent for private events. For public group events, the user is notified that an event was created and sees the standard join action instead. On accepting:
- A full screen with the event image, the "You are in" message, the event date, time and location, a primary "Add to calendar" and a secondary "Close".
- "Add to calendar" opens the native iOS calendar picker. After accepting:
- A "You are going" banner at the top of the event screen, below the header.
- The bottom area no longer carries a leave action — leaving moves into the " ⋯ " menu in the header (UX-JEVT-06). Avatars per UX-GLOB-04.

### UX-JEVT-04

**Location:** Events — Join

**Problem:** The join countdown is always visible, showing the remaining time from the moment the event is created, and there is no full-event or waiting list behaviour at all.

**Suggestion:** The bottom area changes with the event state.
- Open, not invited: a primary "Join" action.
- Approaching the deadline: the remaining time appears to the left of the Join action. The countdown only starts 24 hours before the confirmation deadline — before that, only the Join action is shown.
- Full event: the line "No more spots available" on the left and a "Join waiting list" action on the right.
- On the waiting list: a banner at the top stating the user is on the waiting list, the line explaining that everyone on the list is notified when a spot opens and the spot goes to whoever confirms first, and a secondary "Leave waiting list" at the bottom.
- Closed: the bottom area shows "Event closed" as a static line, with no action. Follows the event rules block.

### UX-JEVT-05

**Location:** Events — Leave Problem: Leaving is a text link in the bottom area rather than an action in the " ⋯ " menu, and once the deadline has passed the screen shows a static line telling the user to contact the organizer, with a "Contactar organizador" row that leads nowhere.

**Suggestion:** Within the deadline:
- "Leave event" lives in the " ⋯ " menu in the header.
- It opens a confirmation sheet stating the user may lose their spot, with a primary "Leave" and a secondary "Cancel". After the deadline:
- The same action opens a different sheet: "Leave", stating that the leave deadline has passed and asking the user to contact the organizer if anything urgent comes up.
- Below it, a card with the organizer photo and name, and two actions — "Chat" opening the conversation, and "Call" opening the phone. Bottom sheet per UX-GLOB-02. Follows the event rules block.

### UX-JEVT-06

**Location:** Events — Event Actions

**Problem:** The " ⋯ " action does not exist on the event screen, so sharing, adding to calendar and leaving have no entry point.

**Suggestion:** The " ⋯ " in the header opens a bottom sheet with:
- Share — opens the native iOS share sheet.
- Add to calendar — opens the native iOS calendar picker.
- Leave event — opens the confirmation defined in UX-JEVT-05. Only shown when the user is confirmed in the event.
- For an organizer who is also playing, this menu appears alongside the settings icon (UX-MEVT-01). Bottom sheet per UX-GLOB-02.

### UX-JEVT-07

**Location:** Events — No Access

**Problem:** The screen does not exist. Opening a private event the user was not invited to has no defined behaviour.

**Suggestion:**
- An empty state with an icon, the title stating the user does not have access, and a description explaining the event is private and only invited players can see the information.
- A close ( ✕ ) in the header returning the user to Home. Not a back arrow — the screen is usually reached from a link, so there is no previous step to return to. Header per UX-GLOB-01. Empty state per UX-GLOB-03.

### UX-JEVT-08

**Location:** Events — Player List

**Problem:** The screen does not exist. The event shows overlapping thumbnails and a total count, but there is no way to see who is actually in.

**Suggestion:** Reached from the chevron on the players card in the event detail. This is the read-only counterpart of Manage players (UX-MEVT-10) — same structure, no actions.
- Back button and title "Players".
- Tabs, each labelled with its count: Confirmed (8/16), Waiting list (5), Invited (2). The waiting list tab only appears when the event has one.
- Player rows with photo and name, each opening that profile.
- No swipe actions, no remove, no promote — nothing on this screen acts on a player.
- A player added manually by the organizer carries a guest tag and has no chevron, since there is no profile to open. Header and back button per UX-GLOB-01. Empty state per UX-GLOB-03. Avatars per UX-GLOB-04.

### UX-JEVT-09

**Location:** Events — Team Event

**Problem:** A team event is indistinguishable from a regular one. Nothing on the screen indicates that entry requires a pair. The "Aderir com um parceiro" action only surfaced after joining and leaving the event, which is a bug. Tapping it leads to a "Pedidos de parceiro" screen showing an empty invitation list — but at that point the user has not been invited by anyone; they are the one who should be choosing a partner. The whole team flow is inverted.

**Suggestion:** A team event must announce itself as one from the start.
- The event detail shows the format badge as a team format.
- The join action reads "Join", as in any other event. Whether the user has a partner is asked in the next step, not in the label.
- The action is available in the normal state, not only after joining and leaving.
- Tapping it opens a bottom sheet titled "Team Event", explaining this is a team event and asking how the user wants to set their team, with two selectors, each with a chevron: I have a partner and I need a partner, plus a "Cancel" action.
- The partner requests screen is not the entry point for joining. It only lists invitations the user has received from others (UX-JEVT-12). • Spots are counted per player, as in any other event. A confirmed pair fills two; a player looking for a partner fills none. Bottom sheet per UX-GLOB-02.

### UX-JEVT-10

**Location:** Events — I Have a Partner

**Problem:** The screen does not exist. There is no way to pick who will play with you.

**Suggestion:** Reached from "I have a partner" in the Team Event sheet.
- Back button and title "I have a partner", with the line "Choose your partner" below it.
- Search input at the top, and "+ Add manually" alongside it.
- A list of the players invited to the event, each with photo, name and a single-selection control. In a public group event, that list is the whole group.
- Selecting one enables the primary "Confirm" action; a secondary "Cancel" sits below it.
- Above the actions, a line stating that choosing a partner confirms both spots in the event.
- Confirming places both players in the event as a pair, with no acceptance step from the other player. This mirrors how padel pairs are arranged in practice — players agree beforehand and then one of them registers the pair.
- On success, the "You are going" screen appears showing the partner photo and name, the event date, time and location, with "Add to calendar" and "Close". Add manually:
- Opens a bottom sheet with a name field, for playing with someone who is not on the app.
- The note warns this should only be used for someone who has no access to the app and will not have it before the event. The player is created and confirmed for this event only, carries no history, appears in no ranking, and cannot be reused in another event.
- Saving confirms the pair, the same as selecting an existing player.
- When the search returns nothing, show the standard empty state with "Add manually" as its CTA. Bottom sheet per UX-GLOB-02. Empty state per UX-GLOB-03. Avatars per UX-GLOB-04. Search input per UX-GLOB-05.

### UX-JEVT-11

**Location:** Events — I Need a Partner

**Problem:** The screen does not exist. There is no way to look for a partner among the other players. Suggestion: Reached from "I need a partner" in the Team Event sheet.
- Back button and title "I need a partner", with the line explaining that players invited will be notified once they accept.
- Search input at the top.
- A list of the other players who also selected "I need a partner", each with photo, name and an "Invite" action that changes to "Invited" once sent.
- The user can invite more than one player. Whoever accepts first becomes the partner, and every other invitation they sent is withdrawn automatically. Someone with a preferred partner in mind should invite only them.
- A primary "Confirm" action, and a secondary "Let others invite me" below it, which lists the user among those looking for a partner without sending any invitation.
- Both paths result in the same state: the user is marked as interested. The organizer sees no distinction between someone who sent invitations and someone who only listed themselves (UX-MEVT-14).
- When nobody else has selected "I need a partner", show an empty state stating that no one is looking for a partner, explaining the user will appear in this list for upcoming players who are looking, with the "Confirm" action still available.
- Spots are filled per player, in the order pairs confirm. A user marked as interested fills no spot — if two other players confirm as a pair while they are still looking, that pair takes the spots. When the event fills up before the user finds a partner, they move to the waiting list as a pair once they do confirm one. Empty state per UX-GLOB-03. Avatars per UX-GLOB-04. Search input per UX-GLOB-05.

### UX-JEVT-12

**Location:** Events — Partner Requests

**Problem:** The screen exists but is used as the entry point for joining a team event, which is wrong — it should only hold invitations received from other players. It also shows a bare line of text when empty.

**Suggestion:** This screen lists only partner invitations the user has received.
- Reached from a "Partner Requests" entry at the top of the Notifications list, showing the pending count and a chevron.
- Partner invitations are also highlighted in the notifications list itself.
- Requests grouped by event, with the event name as the heading and the date, time and venue as a secondary line.
- Each row shows the requester photo and name, with "Decline" as secondary and "Accept" as primary.
- Accepting opens a confirmation sheet explaining that accepting confirms the user participation in the event and automatically declines every other partner request they have for that event, and that declined users are not notified. On confirming, both players are confirmed as a pair and the invitation disappears from the list.
- Declining removes the invitation from the list. The player who sent it receives no notification. • When there are no requests, show the standard empty state, not a line of text. Bottom sheet per UX-GLOB-02. Empty state per UX-GLOB-03. Avatars per UX-GLOB-04.

### UX-JEVT-13

**Location:** Events — Interested State

**Problem:** There is no state between wanting to play and being confirmed, so a user looking for a partner has no way to see or change their situation.

**Suggestion:** A user who selected "I need a partner" is marked as interested.
- A "You are interested" banner at the top of the event screen.
- Above the bottom action, a line stating they are marked as interested and will be automatically confirmed once they have a partner.
- The bottom action reads "Edit response", opening a bottom sheet with three rows: – I found a partner — opens UX-JEVT-10 to pick someone and confirm both. – I need a partner — reopens UX-JEVT-11 to invite more players or withdraw invitations already sent. – Leave event — removes the user from the interested list and cancels every invitation they sent.
- A "Cancel" action closes the sheet. Bottom sheet per UX-GLOB-02.

### UX-JEVT-14

**Location:** Events — Leave Team Event

**Problem:** Leaving a team event has no defined behaviour for the partner who stays.

**Suggestion:**
- When a confirmed player leaves a team event, their partner does not leave with them.
- The partner returns to the invited state, keeping their spot but without a pair.
- They are notified that their partner left and that they need to set a team again.
- The event screen returns to the team event entry state, with the join action available. Follows the event rules block.
